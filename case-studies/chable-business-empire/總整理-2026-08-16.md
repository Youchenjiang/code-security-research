### 3.1 買店卡點的最終定論(2026-08-16)

**purchaseStoreV1 的合法請求需要三件事,前兩件已過、第三件是死結:**

1. **正確 schema**(16 無條件 + 4 條件鍵)— ✅ blutter 還原 + probe42 實測過鍵檢查
2. **listing 在該帳號 scan cache** — ✅ test_pentest_03 高雄小港有真實 cache(08-15 真機)
3. **`officialBusinessId`(ob)真值** — ❌ **純 API 三路全封**:
   - resolve 回應無 ob(probe43,欄位全集固定 6 鍵)
   - Firestore `official_businesses` 403(實測)
   - ob = `generateId() = "<epochMicros>_<nextInt(99999)>"` 隨機 ID,名字爆破 82 候選全 not found(probe44)
   - 已購店(034)與第三方店(022/松崗/新厝洗車/環帶 7 間)的 ob 也推不出來(probe45 + Store 模型
     逆向:ob 不離開 client;⚠️ 022 非本帳號店,probe49 更正;probe50/51:第三方店共 10 間)

**結論:P1 價格信任維持「未達成」,唯一解鎖路 = root/debug 裝置(或 App Check token 重放)。**

### 4.2 輸入驗證漏洞(低危,可通報)

- **storeId / takeoverId 含 `/` → 多函式 500 未處理例外**(probe34/35/37):
  `queueGameplayActionV1`(catch 後 `Takeover action failed unexpectedly.`)、
  `configureInitialMaintenanceV1`/`sellStoreV1`/`syncBrandNameToGlobalV1`(裸 INTERNAL)。
  假 ID 也 500 → 與 store 存在無關,任何登入使用者可打掛處理器。
- resolve 對 ob 含 `/` 的值也 500(probe43 次要發現)。

### 4.3 中低危觀察(產品面,非漏洞)

- **既有帳號自動化未根除**:refresh token 豁免 App Check(Firebase 設計)+ functions 未 enforcement
  → 08-14 前的 bot 帳號可無限續命、純 HTTP 自動化免費面。有界,無公平性影響。
- **App Check 鎖定範圍過寬**:模擬器/root 連登入都被擋(over-blocking 是安全失敗方向,產品決策)。
- **廣告獎勵無回執驗證**(grantActionChargeRewardV1 呼叫即給點)——靠伺服器冷卻限流,屬設計。

### 4.4 防守性設計(正面確認,無漏洞)

- 掃描快取寫入 = 唯一經濟鏈閘門,且未被攻破。
- storeId 不透明(伺服器 Firestore doc ID,任何 OSM 衍生格式皆 not-found)。
- admin 檢查在參數驗證之前。
- 執照二次方定價、冷卻/行動點數有交易保護、推薦有界(每碼 2 上限)。
