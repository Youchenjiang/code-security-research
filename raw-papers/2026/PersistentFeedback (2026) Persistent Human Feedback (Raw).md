III. M ANUAL VS . A UTOMATED A NALYSIS T OOLS

To identify opportunities to improve the security of LLM-

generated code, assess the reliability of results from static

analysis tools, and determine whether static analysis tools and

LLMs are sufficient on their own, we designed a study using

the dataset from Bruni et al. [7]. Their work uses two pop-

ular peer-reviewed datasets LLMSecEval and SecurityEval to

generate code with LLMs and to evaluate multiple prompting

strategies across different GPT models in order to determine

which is most effective. They also apply two widely adopted

static analyzers, Semgrep and CodeQL, to assess the security

of the generated code. Because their setup is comprehensive

and representative, we use their data as our starting point.

Improvement) prompting technique with GPT-4o yields the

most secure code [7]. We therefore use this configuration as

B. Result

We found that 39% of the generated code samples were

vulnerable and 61% were secure. We evaluated each code

sample only with respect to its designated target CWE and

did not investigate the presence of other, non-target CWEs. In

other words, samples that we labeled as secure with respect to

their specific target CWE may still contain other, non-target

CWEs. Figure 1 presents the distribution vulnerable and secure

samples for each target CWE.

We noted two main forms of self-critiques in the results

for each task. General critique offers broad guidance with-

out concrete references to the snippet or CWEs (e.g., “use

secure functions”, “sanitize inputs”), whereas specific critique

provides targeted, actionable feedback tied to the snippet (e.g.,

naming APIs or lines, citing the relevant CWE, and prescribing

critiques yielded more secure code than general self-critique:

64% secure versus 56%, respectively.
